Project Context

Conducted a comprehensive threat modeling exercise for an e-commerce payment platform developed by Industrias Vaine (fictitious company), requiring PCI DSS v4.0 compliance for cardholder data processing.

The threat model was integrated into the Secure SDLC process from the design phase, applying multiple threat modeling methodologies to ensure defense-in-depth coverage of the payment processing architecture.

STRIDE Threat Analysis

Applied the STRIDE methodology to systematically identify threats across all six categories for each trust boundary in the e-commerce architecture:

DREAD Risk Scoring

Applied the DREAD scoring model to quantify and prioritize identified threats based on five dimensions (Damage, Reproducibility, Exploitability, Affected Users, Discoverability), each scored 1–10:

DREAD Scoring Dimensions

  • Damage potential (D): How bad would an attack be? (1 = minimal, 10 = catastrophic)
  • Reproducibility (R): How easy is it to reproduce? (1 = very hard, 10 = always)
  • Exploitability (E): How easy is it to launch? (1 = advanced skills, 10 = script kiddie)
  • Affected users (A): How many users impacted? (1 = none, 10 = all)
  • Discoverability (D): How easy to discover? (1 = very hard, 10 = obvious)

Threats scoring above 7.0 average were classified as Critical and required immediate mitigation in the SDLC design phase. Medium threats (4–7) were scheduled for sprint-level remediation, and low threats (<4) were accepted with monitoring.

TAMT & Data Flow Diagrams

Used the Threat Assessment and Mitigation Table (TAMT) to systematically document each threat, its risk rating, applicable mitigations, and responsible controls:

TAMT Structure

  • Threat ID and STRIDE classification
  • DREAD score and overall risk rating (Critical / Medium / Low)
  • Data Flow Diagram (DFD) element affected (process, data store, external entity, data flow)
  • Trust boundary crossed
  • Applicable mitigations mapped to PCI DSS requirements
  • CWE weakness identifiers for developer reference
  • Status (Open / Mitigated / Accepted)

Data Flow Diagram (DFD) Elements

The DFD modeled the following trust boundaries in the e-commerce architecture:

  • Internet → Web Application (WAF boundary)
  • Web Application → Payment Gateway (TLS + mTLS boundary)
  • Application Server → Database (Internal network boundary)
  • Database → Log Aggregation (Monitoring boundary)
  • Admin Panel → Management Functions (Privileged boundary)

Abuse Cases

Developed abuse cases as the negative counterpart to use cases, describing how each system function could be misused by malicious actors:

Example Abuse Cases

  • UC-01 / AC-01: Place Order → Attacker manipulates price parameter before payment submission
  • UC-02 / AC-02: Process Payment → Attacker captures PAN via MITM on unencrypted channel
  • UC-03 / AC-03: View Order History → Attacker accesses another user’s orders via IDOR
  • UC-04 / AC-04: Admin Panel Login → Attacker brute-forces admin credentials with no rate limiting
  • UC-05 / AC-05: Store Card Data → Attacker extracts stored PANs via SQL injection in search function
